## Objetivo

Adicionar exportação CSV, XLSX e PDF às visões canônicas de `/relatorios`, garantindo que os três formatos representem o mesmo recorte financeiro sem recalcular regras no renderer de arquivo.

## Fontes canônicas

- `docs/REPORTS.md`
- `docs/API_REPORTS.md`
- `docs/reports/accountant-csv-export.md` como referência de segurança/tenant para exportação
- `docs/PRODUCT.md`
- `docs/EVOLUTION_STRATEGY.md`

## Escopo do primeiro corte

Exportar as três visões já existentes em `/relatorios`:

- `category-evolution`;
- `installments`;
- `cash-flow`.

Os filtros aceitos por cada visão continuam sendo exatamente os contratos canônicos já documentados. A exportação não cria um quarto conjunto de filtros nem uma nova semântica financeira.

## Fora de escopo

- Conversão cambial.
- Novos cálculos de relatório.
- Alterar semântica de filtros, períodos ou fontes existentes.
- Relatório fiscal/legal oficial.
- Exportar dados de outro perfil por parâmetro livre.
- Incluir anexos ou dados sensíveis que não façam parte do recorte exibido.

## Invariantes

1. **must_reuse:** CSV/XLSX/PDF devem consumir o mesmo resultado canônico do relatório; renderer de arquivo não recalcula saldo, resultado, parcelas ou projeção.
2. **must_be_single_source:** filtros/periodicidade/moeda do relatório são a fonte de verdade da exportação.
3. **must_not_behave:** moedas diferentes nunca são somadas para formar total único.
4. O recorte autorizado deve ser idêntico ao que a API de relatório devolveria para o mesmo contexto.
5. Texto controlado pelo usuário deve ser serializado de forma segura para planilhas/CSV, sem permitir formula injection.

## Requisitos funcionais

- A ação de exportar preserva `view`, período, origem financeira e demais filtros válidos da URL atual.
- `profileId` nunca substitui a autorização do contexto autenticado.
- CSV e XLSX devem manter códigos de moeda explícitos e dados tabulares suficientes para reconstruir o recorte.
- PDF deve apresentar o mesmo recorte de forma legível, incluindo moeda, período/filtros e estado vazio quando aplicável.
- Quando houver mais de uma moeda, cada uma permanece em bloco/seção identificável.
- O arquivo deve carregar metadados suficientes para identificar visão, filtros e período; timestamp de geração pode existir, mas não altera a equivalência dos dados.
- Estado sem dados gera artefato válido e controlado, não erro técnico.
- Filtro inválido continua sendo rejeitado pelo contrato do relatório; a exportação não corrige valor silenciosamente.

## Equivalência semântica

Para o mesmo snapshot e filtros:

- os mesmos itens/grupos monetários devem existir nos três formatos;
- totais, períodos, moedas e estados devem coincidir com a resposta canônica;
- diferenças de apresentação/ordenação próprias do formato são permitidas apenas quando não alterarem significado.

## Critérios de aceite

- [ ] As três visões atuais de `/relatorios` podem ser exportadas em CSV, XLSX e PDF.
- [ ] Todos os formatos reutilizam o resultado canônico, sem cálculo financeiro duplicado.
- [ ] Filtros, período, perfil autorizado e moeda são preservados.
- [ ] Multi-moeda permanece separada sem conversão ou total implícito.
- [ ] Estado vazio produz arquivos válidos.
- [ ] Texto potencialmente perigoso é neutralizado em CSV/XLSX.
- [ ] Testes comparam semanticamente os três formatos contra o mesmo fixture/snapshot canônico.
- [ ] `docs/REPORTS.md` deixa de listar exportação como fora de escopo e documenta campos/limites dos formatos.

## Considerações de testes

Cobrir as três visões, dois perfis isolados, duas moedas, filtros válidos/inválidos, vazio, caracteres especiais, formula injection e equivalência de valores entre formatos.
