## Objetivo
Separar os dados bancários de agência e conta no cadastro de contas financeiras, substituindo o único campo visual `Nº Conta` por dois campos independentes: `Agência` e `Conta`.

## Contexto
Hoje o modal de criação/edição de conta usa um único campo `maskedIdentifier`, inclusive com agência e conta combinadas no mesmo valor. O domínio `Account`, o router de contas, o repositório PostgreSQL, o schema Prisma e a listagem web ainda carregam esse campo legado. Isso impede tratar, editar e evoluir agência e conta de forma independente.

O campo legado já é usado como apresentação minimizada, inclusive com a convenção documental `Final 1234`. A mudança deve introduzir os dados estruturados sem tentar decompor valores históricos potencialmente ambíguos.

## Escopo
- No modal **Nova conta**, exibir um campo `Agência` e outro campo `Conta`.
- Aplicar a mesma separação no modal de edição para preservar o round-trip dos dados estruturados.
- Persistir `agencyIdentifier` e `accountIdentifier` em colunas separadas e opcionais no modelo `Account`.
- Expor os dois valores separadamente no domínio e no contrato da API de contas.
- Manter compatibilidade de leitura com `maskedIdentifier` para registros existentes.
- Manter a listagem reconhecível com apresentação minimizada, sem colocar os novos valores completos no conteúdo renderizado ou nos metadados usados pela busca.
- Atualizar testes e documentação afetados.

## Fora de escopo
- Alterar o modelo de cartões ou instrumentos de cartão.
- Tentar migrar ou decompor automaticamente conteúdo histórico de `maskedIdentifier` para agência/conta por heurística.
- Concatenar novamente agência e conta para persistir um novo `maskedIdentifier`.
- Alterar instituição, tipo, moeda ou saldo inicial da conta.
- Remover a coluna legada `maskedIdentifier` nesta entrega.

## Requisitos funcionais

### 1. Modelo, persistência e API
1. `Account` deve expor `agencyIdentifier?: string` e `accountIdentifier?: string` separadamente.
2. `POST /api/accounts` deve aceitar `agencyIdentifier` e `accountIdentifier` separadamente.
3. `PATCH /api/accounts/:accountId` deve permitir atualizar cada campo independentemente.
4. Ambos são opcionais.
5. Quando um dos campos for informado, o valor deve ser normalizado com `trim` antes da persistência.
6. Em `POST`, campo ausente ou cujo valor normalizado seja vazio deve ser persistido como ausência (`NULL`/propriedade omitida), não como string vazia.
7. Em `PATCH`:
   - campo omitido preserva o valor persistido;
   - campo presente com texto não vazio substitui somente aquele identificador;
   - campo presente cujo `trim` resulte em vazio limpa somente aquele identificador, persistindo ausência (`NULL`/propriedade omitida).
8. A migration deve ser aditiva: criar as duas colunas opcionais sem backfill heurístico e sem remover ou reescrever `maskedIdentifier` em massa.
9. As respostas de criação, leitura, listagem e edição devem retornar os novos campos quando existirem.

### 2. Compatibilidade legada e precedência
1. `maskedIdentifier` permanece legível para registros históricos que ainda não possuam os novos identificadores.
2. `maskedIdentifier` nunca deve ser usado para derivar automaticamente `agencyIdentifier` ou `accountIdentifier`.
3. `maskedIdentifier` deixa de ser fonte gravável do contrato de contas: `POST` e `PATCH` não devem criar ou atualizar esse campo a partir do payload e não devem usá-lo como substituto dos novos campos.
4. Em um registro legado sem os novos campos, editar nome, instituição, tipo, moeda, saldo ou status não deve apagar nem alterar `maskedIdentifier`.
5. Quando o usuário salvar ao menos um dos novos identificadores em um registro legado, o valor legado não deve ser interpretado nem concatenado com os novos campos. Os novos campos passam a ser a fonte preferencial para apresentação e edição.
6. Se um objeto contiver simultaneamente novos identificadores e `maskedIdentifier`, a UI deve usar os novos campos como fonte preferencial; `maskedIdentifier` é fallback somente quando `agencyIdentifier` e `accountIdentifier` estiverem ambos ausentes.
7. O modal de edição de um registro que possua somente `maskedIdentifier` deve abrir `Agência` e `Conta` vazios; não deve tentar pré-preenchê-los a partir do texto legado.

### 3. Interface
1. O modal **Nova conta** deve substituir o campo visual único `Nº Conta` por dois campos independentes:
   - `Agência` → `agencyIdentifier`;
   - `Conta` → `accountIdentifier`.
2. O modal de edição deve usar os mesmos campos e preencher somente os valores estruturados efetivamente persistidos.
3. O formulário de criação e edição não deve concatenar agência e conta nem enviar `maskedIdentifier`.
4. Deve ser possível salvar:
   - ambos os campos;
   - somente agência;
   - somente conta;
   - nenhum dos dois.
5. Limpar um dos campos em edição não pode limpar o outro.

### 4. Listagem e privacidade
1. A listagem não deve renderizar os valores completos de `agencyIdentifier` ou `accountIdentifier` nem inseri-los integralmente em `data-search` ou atributo equivalente.
2. Quando houver novos identificadores, a listagem deve usar uma representação derivada e minimizada que:
   - revele somente um sufixo do identificador;
   - não revele o valor integral;
   - substitua/oculte ao menos parte do valor original;
   - mantenha contexto suficiente para reconhecimento, seguindo a convenção visual existente de identificador minimizado, como `Final …`.
3. Se um valor for curto demais para ser exibido parcialmente sem revelar o conteúdo integral, ele não deve ser mostrado na listagem.
4. `maskedIdentifier` pode continuar sendo apresentado como fallback para registros legados somente quando os dois novos identificadores estiverem ausentes.
5. Os valores completos continuam disponíveis apenas nos fluxos autorizados de edição/API que já retornam o recurso, sem serem copiados para logs, mensagens de erro, fixtures reais ou documentação.

## Cenários e casos extremos
- **Criação com ambos os campos:** agência e conta são aparadas, persistidas e retornadas separadamente.
- **Criação parcial:** somente agência ou somente conta permanece válida; o outro campo fica ausente.
- **Criação com espaços:** valor composto apenas por espaços é tratado como ausente.
- **Edição independente:** atualizar agência não altera conta e vice-versa.
- **Limpeza independente:** enviar `"   "` em um dos campos limpa apenas aquele valor.
- **PATCH omitido:** omitir um identificador preserva seu valor atual.
- **Registro legado:** conta com apenas `maskedIdentifier` continua legível e a listagem usa o fallback legado.
- **Edição de registro legado:** os novos inputs ficam vazios e salvar outro atributo preserva o fallback legado.
- **Registro híbrido:** se houver novos campos e `maskedIdentifier`, a apresentação usa os novos campos e não o legado.
- **Valor legado ambíguo:** nenhuma string histórica é dividida, inferida ou usada para preencher os novos campos.
- **Privacidade da listagem:** valores sentinela completos de agência/conta não aparecem no HTML renderizado nem no índice textual de busca.

## Invariantes estruturais

### `must_not_behave`
- Não fazer parsing, split, regex ou heurística sobre `maskedIdentifier` para gerar os novos campos.
- Não concatenar `agencyIdentifier` e `accountIdentifier` de volta em `maskedIdentifier`.
- Não expor os novos identificadores completos na listagem ou em metadados de busca.

### `must_be_single_source`
- Para criação e edição novas, `agencyIdentifier` e `accountIdentifier` são as fontes estruturadas dos dados bancários da conta.
- Na apresentação, os novos campos têm precedência; `maskedIdentifier` é apenas fallback legado quando ambos estiverem ausentes.

### `forbidden_implementation`
- **Implementação errada plausível:** dividir `maskedIdentifier` por `/`, `-` ou espaço e preencher agência/conta. Ela poderia passar nos testes de novas contas, mas deve falhar em fixture legada ambígua que precisa permanecer sem novos campos.
- **Implementação errada plausível:** armazenar os novos inputs concatenados em `maskedIdentifier` e apenas separá-los na resposta. Ela poderia passar no caminho feliz visual, mas deve falhar ao inspecionar as duas colunas persistidas e ao editar somente um campo.
- **Implementação errada plausível:** usar sempre `maskedIdentifier` na listagem mesmo quando os novos campos existirem. Ela deve falhar em um registro híbrido no qual o legado esteja propositalmente diferente dos novos valores.
- **Implementação errada plausível:** usar os valores completos no `data-search` enquanto mascara apenas o texto visível. Ela deve falhar em teste SSR que procure os valores sentinela completos no HTML.

## Critérios de aceite
- [ ] O modal **Nova conta** possui campos distintos `Agência` e `Conta` e não possui o campo único `Nº Conta` para contas.
- [ ] Criar uma conta com ambos os campos grava e retorna os valores de forma independente e aparada.
- [ ] É possível informar apenas agência, apenas conta ou nenhum dos dois.
- [ ] Strings vazias ou somente com espaços em `POST` resultam em campo ausente, não string vazia persistida.
- [ ] Em `PATCH`, campo omitido preserva o valor; campo vazio limpa somente aquele identificador; alteração de um não modifica o outro.
- [ ] O schema e a migration adicionam duas colunas opcionais sem backfill heurístico e preservam a coluna `maskedIdentifier`.
- [ ] Registros legados com apenas `maskedIdentifier` continuam funcionando e exibindo o fallback sem parsing heurístico.
- [ ] Editar outro atributo de um registro legado não apaga `maskedIdentifier` nem tenta preencher os novos campos.
- [ ] Quando novos campos coexistirem com `maskedIdentifier`, os novos campos têm precedência na UI.
- [ ] O formulário web não envia `maskedIdentifier` nem concatena agência e conta.
- [ ] A listagem não contém os novos identificadores completos nem no texto visível nem no índice/atributo de busca.
- [ ] Testes de domínio, API/persistência e UI cobrem criação, edição independente, limpeza, compatibilidade legada, precedência e privacidade.
- [ ] `docs/API_ACCOUNTS.md` documenta os novos campos, semântica de `PATCH`, fallback legado e exemplos exclusivamente fictícios/minimizados.

## Considerações de testes

### Domínio
- criação com ambos, somente agência, somente conta e nenhum;
- normalização por `trim`;
- valor vazio normalizado como ausência;
- update independente;
- limpeza independente;
- campo omitido preservando estado;
- ausência de derivação a partir de `maskedIdentifier`.

### API e persistência
- `POST /api/accounts` e `PATCH /api/accounts/:accountId` com os novos campos;
- round-trip das duas colunas no PostgreSQL;
- migration sem backfill e sem remoção da coluna legada;
- leitura de linha antiga contendo somente `maskedIdentifier`;
- update de atributo não relacionado preservando o legado;
- objeto híbrido confirmando precedência dos novos campos;
- payload com `maskedIdentifier` não criando nem atualizando os novos campos.

### Web
- modal de criação com `Agência` e `Conta`;
- modal de edição preenchendo os dois campos separadamente;
- registro legado abrindo ambos os campos vazios;
- criação/edição sem concatenação em `maskedIdentifier`;
- listagem com representação minimizada;
- teste negativo garantindo que valores sentinela completos não apareçam no HTML nem em `data-search`;
- regressão dos fluxos de cartões e instrumentos, que permanecem fora desta mudança.

## Impacto na documentação
- Atualizar `docs/API_ACCOUNTS.md` como fonte canônica do contrato de contas: novos campos, normalização, semântica de `POST`/`PATCH`, leitura legada e regra de privacidade da listagem.
- Atualizar qualquer documentação que ainda descreva `maskedIdentifier` como identificador gravável de `Account` se a busca global encontrar afirmação de estado atual conflitante.
- Não alterar a documentação de cartões apenas por eles continuarem usando `maskedIdentifier`; cartões e instrumentos permanecem fora do escopo.

## Privacidade
Agência e número de conta são dados financeiros sensíveis. Testes, fixtures, documentação e logs devem usar somente valores fictícios/minimizados e nunca registrar dados financeiros reais. A API pode retornar os valores completos somente nos recursos autenticados já autorizados; a listagem deve aplicar minimização antes de renderizar ou indexar esses valores para busca.

## Riscos e dependências
- Um fallback legado sem precedência explícita pode exibir informação antiga mesmo depois de os novos campos serem cadastrados; por isso os novos campos têm precedência.
- Mascarar apenas o texto visível e manter o valor completo em `data-search` ainda constitui exposição no HTML e não atende à privacidade.
- Tentar decompor `maskedIdentifier` pode atribuir agência e conta incorretas a dados históricos e está explicitamente proibido.
- A migration deve ser compatível com registros existentes e não exigir backfill para subir.
